# Design brief

## Product

An independent sports operations console. The central task is to inspect an
event, make a bounded market decision and leave a clear record. RYVQEN is an
original working name and identity; no global name/trademark uniqueness claim
is made.

## Visual language

Charcoal surfaces, fine structural rules, pale text and an electric lime signal.
Cyan distinguishes manual values; warm amber marks paused or failed states.
Color is paired with labels and icons. Space Grotesk supplies the interface
rhythm; IBM Plex Mono supplies compact timestamps, counters and field labels.

The desktop desk places an event radar beside a broad broadcast-style center
and a narrow pulse/journal column. Typography and the authored field diagram
carry the main visual weight. The center stays first on small screens; navigation
moves to a fixed bottom bar and secondary panels follow the task.

All team shields, the brand mark and football/basketball graphics are authored
SVG. Team identities are fictional; there are no copied club marks, stock
dashboard screenshots, template pages or third-party site layouts.

## Motion

Positions interpolate between replay frames. A faint path and a restrained pulse
make the ball legible. Price changes briefly signal the new value, with an arrow
indicating direction. Small bars communicate synthetic possession balance.

Text, actions and essential values do not wait for an entrance animation. The
motion pause preference persists across reloads; system reduced motion disables
transitions and animation as well. Feed values still update when decorative
motion is paused. Feed pause is a separate operational control that blocks edits.

## Content and behavior

English product copy describes what an operator can do. Public labels clearly
identify fictional events and the replay source. The journal begins empty and
records only successfully saved local decisions. No client logos, employer
affiliation, fabricated revenue, security certification or performance score is
presented.

The source is prepared for GitHub Pages with hash routes. README/About must use
the actual verified live URL after deployment; screenshots must come from the
running application.
